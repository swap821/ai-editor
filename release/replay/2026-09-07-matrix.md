## Why half the cases are refusals

A matrix that only walks success paths proves the feature *can* work. Bounded
is the harder claim, and the one that matters for a path that writes files
with no human watching. So four of the eight are refusals, and each asserts
the file as well as the status:

- unapproved create -> blocked, **and the file does not appear**
- unapproved edit -> blocked, **and the file is unchanged**
- existing file with different content -> blocked, **and the original survives**
  (`create_file` refuses to overwrite; repairing that file needs an edit)
- neither side of an edit present -> abstained, and **not** permanently, so the
  playbook is not retired over a file that simply drifted

Both confirm cases assert the **mtime is unchanged**. "Confirmed" has to mean
no write happened, not that identical bytes were rewritten — the two are
indistinguishable by content alone, which is exactly how a no-op claim rots.

## What this does NOT establish

**Not a real-world confirmation rate.** Every case here was constructed. The
open question from #316 stands untouched: if recorded files are usually stale
by replay time, every playbook abstains and the practical gain is near zero.
That number needs sustained real use, which does not exist yet and cannot be
manufactured in a session.

What it does establish is narrower and was genuinely unknown: with the flag on,
against a filesystem, the path works and the refusals hold.
